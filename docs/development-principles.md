# 开发原则

这份文件可单独交给 Codex 或 Claude Code，作为 Market Monitor 的开发准则。项目用于本人在个人笔记本上看盘、筛选和复盘，只有一个使用者，当前不是生产运营系统。目标是把核心功能做好，保持简单、稳定、容易理解和维护。

## 工作优先级

1. **只开发核心功能，并保证鲁棒稳定。** 行情与名单的数据含义正确，核心流程可靠，实际失败有清楚的错误，不能悄悄通过坏数据或冒充成功。
2. **满足用户当前要求。** 当前要求优先于其他文档；先理解本轮实际用途、范围和预期结果，遇到真正影响实现的歧义与本人讨论。
3. **选择直接、简单的实现。** 优先复用或者简化项目现有结构，禁止通过加 patch 形式实现；减少重复逻辑、额外状态和维护成本。
4. **控制复杂度与范围。** 困难边界或需求冲突先说明问题并讨论取舍，不擅自增加复杂机制，也不顺手开发无关功能。
5. **用必要证据完成工作。** 验证本轮改动，说明结果及尚未覆盖的实际问题；同步受影响的唯一文档入口，不堆叠重复说明。

## 实现边界

- 不为单人本机项目过度设计或过度开发，不为假想的未来规模、客户端或使用场景提前建设架构。
- 不引入本轮需求不需要的服务拆分、消息中间件、负载均衡、通用适配层或通用框架。
- 禁止添加防御性编程：不为罕见边界、假想故障或模糊需求增加防御分支、通用回滚、自动兜底或恢复框架。难以判断的 case 与本人讨论是否调整需求。
- 当前明确需要的数据校验、接口契约和清楚错误属于核心业务要求，直接落实；不能以“保持简单”为由吞掉错误或静默接受不符合要求的数据。
- 可从原始数据重建的派生文件，失败直接报错，重新生成即可；不为保留失败前的副本增加复杂事务、迁移、逐项修复或回滚机制。

## 验证方式

- 围绕本次修改选择必要、相关的验证，优先使用项目已有真实数据，确认真实结果是否满足要求。需要真实接口时，明确本次验证对象与结束条件。
- 可以直接使用本机现有服务；本次开发验证确需停止或重启服务时，直接操作，不重复请求确认。避免把已有运行记录当作本轮验证证据。
- 离线用例用于补足本次改动涉及的规则、边界和错误路径；测试应验证有意义的行为，而不是复写实现。
- 不无故扩展为全流程验收、并发压力测试、故障注入、回放或性能框架；不为低风险、可逆改动添加没有实际价值的测试。
- 性能优化按当前瓶颈做必要对照，记录数据范围和耗时即可，不把一次优化发展成长期测试基础设施。

## 完成前检查

- 当前要求与核心用途是否已经满足？实现是否仍然直接、简单？
- 是否引入了没有实际需要的功能、状态、分支或架构？
- 必要验证是否完成，结果与未覆盖范围是否说明，相关文档是否同步？
